## [2026-11-03] Releases from version tags

**Type**: Config
**Author**: agent

### What changed

Added `.github/workflows/release.yml`: pushing a tag `vX.Y.Z` runs typecheck, lint and tests, restores the signing key from
four repository secrets, builds the signed APK with `npm run android:apk`, verifies it with `apksigner` against a pinned
certificate fingerprint, and publishes a GitHub release with `SkyHop.apk` and `SkyHop.apk.sha256`. The README download link
is now `releases/latest/download/SkyHop.apk`, so it always serves the newest version. `downloads/` is git-ignored (the APK is
no longer committed). `scripts/build-apk.mjs` starts Gradle through `sh` on Linux and macOS so the wrapper's executable bit
does not matter.

This supersedes the decision in the entry below to commit the APK.

### Why

The owner wants every new version available from the README download button, as in their StatsInfo project, where a pushed
version tag triggers a build and a release.

### Files touched

- `.github/workflows/release.yml`, `scripts/build-apk.mjs`, `.gitignore`, `README.md`

### Validation

The workflow YAML parses; its tag-versus-`package.json` step, run as written, passes for `v2.0.0` and fails for `v2.0.1`,
`vfoo`, `v2.0` and `v2.0.0-beta`. A keystore passed through base64 and decoded as the workflow does is byte-identical and
signs an APK whose certificate matches the pinned fingerprint, and the workflow's verify step rejects an APK signed with a
different key. Not verified: the Linux runner build, the Android SDK install step, and the GitHub release step; the workflow
has never run on GitHub, so expect one round of fixes. The owner must add four repository secrets
(`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`) before the first tag,
and the first release is `v2.0.0`. The repository name in the README links (`gopichandchikoti/SkyHop`) is an assumption.

## [2026-11-03] Bird centred on screen

**Type**: Fix
**Author**: agent

### What changed

The bird was drawn a quarter (portrait) or 30% (landscape) of the way across the screen. The camera now sits on the
bird's x, so the bird is horizontally centred at every aspect ratio. Because the view now reaches up to about 32 world
units behind the bird (it used to be about 19 at most), pipes despawn at x = -34 instead of -10; otherwise they would
have vanished on screen on 16:9 and wider displays.

### Why

The owner reported the bird sitting at the left instead of the middle. The old offset was a deliberate look-ahead
choice in `computeFraming`, so this reverses that design decision at their request.

### Files touched

- `src/render/stage.ts` (`computeFraming`: `camX` is now `WORLD.birdX`)
- `src/core/config.ts` (`despawnX` -10 to -34)
- `tests/render-logic.test.ts` (centred-bird expectations, new despawn-distance test),
  `tests/pipes-collision.test.ts` (despawn test follows `WORLD.despawnX` instead of a magic distance)

### Validation

`tsc --noEmit` exit 0. 211 unit tests pass; coverage 99.44 / 96.57 / 98.80 / 99.87 %. `eslint` on the four touched
files exit 0. `npm run test:e2e` (real Edge, dev server on 5605): 14 passed, 0 failed. A scripted browser run at 390x844
and 1280x720 showed the bird at about 50% across (menu, ready and playing), no console errors, and a pipe that had
passed the bird (x about -12) still drawn; the smallest pipe x seen in play was -33.96, so the new despawn distance is
exercised.

Not verified: play feel on a real phone, and the rebuilt APK (the installed APK still has the old framing until
`npm run android:apk` is run). `eslint .` currently fails on `scripts/make-android-icons.mjs` (a 122-character comment
line); that file changed while this work was running and is not part of this fix.

### Known trade-off

On a portrait phone the bird now sees about 6.25 units of pipe ahead instead of about 9.4, which is roughly 0.9 s instead
of 1.4 s of warning at the top level speed (6.72 u/s). When the bird flies near the top it can pass behind the centred
score and progress bar.
